# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

BrassCount is an Android-only React Native (0.86, React 19, TypeScript 6) shot-timer app for shooting drills: a randomised start beep, a running timer with per-step par times, drill/sequence editing, mic calibration, and run history. There is no `ios/` directory. Requires Node >= 22.11.

## Commands

```bash
npm start                  # Metro bundler
npm run android            # Build + run debug on device/emulator (needs JDK 17, JAVA_HOME)
npm run android:release    # Release APK (android:bundle for AAB, android:clean to clean)

npm test                   # Jest (single run, not watch mode)
npm test -- startSequence  # Single test file (path pattern)
npm test -- -t "waits the random delay"   # Tests matching a name
npm run test:ci            # Jest with coverage, as CI runs it
npm run android:test       # Kotlin JVM unit tests (gradlew testDebugUnitTest)

npm run typecheck          # tsc --noEmit
npm run lint               # ESLint, --max-warnings=0
npm run format:check       # Prettier check (CI gate)
npm run lint:format        # eslint --fix + prettier --write
```

Before pushing, the PR gate is: `lint`, `format:check`, `typecheck`, `test:ci`, plus the Kotlin unit tests (`testDebugUnitTest`) and an Android `assembleDebug` build. CI copies `.env.example` to `.env` before the Gradle build.

## Architecture

### Current state: UI is ahead of the data layer

The screens are a finished front-end pass rendered from **fixtures**, not real data. `src/constants/previewData.ts` holds both the display fixtures (`previewDrills`) and, for now, the drill domain types and helpers (`DrillStep`, `SequenceAction`, `countShots`, `totalParSeconds`, `labelForStep`). Its header says to swap each `preview*` export for a real selector when the data layer lands, then delete the file.

`src/services/` is being built up one service at a time and wired into screens as each lands. So far `StartSequenceService` and `DrillRunEngine` are consumed by `TimerScreen` (via `useDrillRun`; see "Timing a run" below), and `ProfileScreen` reads the profile through `ProfileStorageService` and its Runs / Drills counters from `SessionStorageService` / `DrillStorageService` (via `useProfileOverview`, which re-reads on tab focus), and `DrillsScreen` lists the stored drills from `DrillStorageService` (via `useDrills`, which re-reads on focus) and deletes one (see "Deleting a drill" below), and `HistoryScreen` lists the drills that have been run from `SessionStorageService` and `DrillStorageService` (via `useDrillHistory`; see "History list" below), and `HistoryDetailScreen` lists the runs of one drill from the same two services (via `useDrillRuns`; see "History detail" below). `SequenceEditorScreen` is the screen that creates and changes drills: it builds a drill in local state (see "Drill editor" below), opened with the `id` of a stored drill it starts from that drill, and its save button creates or updates the drill through `DrillStorageService`. No screen writes sessions yet — the Timer times a run but does not save it — so the Runs counter stays at 0 and the History list is empty on a real install, and the Timer's drill chips still show fixtures — a drill made in the editor shows on the Drills list and in the Drills counter, not yet on the Timer. The stored drill model is `src/types/drill.ts` (`Drill`, steps as `{ id, type, par }`), which the Drills screen and the editor use; the Timer screen still lists the fixture drills (`{ action, parSeconds }`) and maps each to that shape, with made-up step ids, to hand to the engine. A run in progress is `src/types/run.ts` (`RunStep`, `StepResult`, `RunResult`); nothing in it is stored. The stored run model is `src/types/session.ts` (`Session`: `drillId`, `totalTime`, and splits as `{ stepId, label, par, actual, delta }`); the History list and the History detail screen both read it. The stored profile model is `src/types/profile.ts` (`Profile`: `name`, `handle`, `appearance`, `updatedAt`); the Profile screen shows and edits the name and handle, and its Appearance row opens `AppearanceSheet` to pick System / Light / Dark (see "Appearance state" below). The screen has no "Sign out" row: there is no account to leave.

There is no state-management library — screens use local `useState`/`useRef`. The two pieces of shared state are calibration and the Appearance preference (see below). There is no `src/api/` despite the alias existing.

### Calibration state (`src/store/`)

Per-sound calibration (`shot`, `reload`, `rack`: threshold, status, last test reading) lives in a React Context: a pure reducer in `calibrationReducer.ts`, `CalibrationProvider` in `CalibrationContext.tsx` mounted in `App.tsx` above the navigators, read through `useCalibration()`. It is **deliberately in-memory only** and resets when the app is closed — do not persist it through `storage.ts`. Levels are dBFS, the unit `AmplitudeReading` reports, so a threshold compares directly with a live reading. Levels pass through `normalizeDbfs` before dispatch: anything below the -160 floor (silence reads as `-Infinity`) is raised to it, so a reading off the mic stream never throws, while `NaN` or a level above 0 throws `CalibrationError` as a caller bug. Keep the live microphone level out of this store; it changes many times a second.

`CalibrationScreen` draws one card per sound from this state: status chip, a meter over -60 to 0 dBFS filled to the threshold with a tick at the last test reading, and Threshold / Last test readouts. Recalibrate and Test are wired to the microphone through `useCalibrationCapture` (`src/hooks/`), which runs one capture at a time with `CalibrationCaptureService` and writes the result to the store: **Recalibrate** sets the threshold `THRESHOLD_MARGIN_DB` (6 dB) below the loudest peak of a `CALIBRATION_LISTEN_MS` (3 s) window, and keeps the old threshold when the peak never reaches `MIN_SAMPLE_DBFS` (-60, "No sound heard"); **Test** records the window's loudest peak as the last test reading. Those rules are pure functions in `src/utils/calibration.ts`. A test's pass or fail is not stored — `testOutcome` derives it from the threshold and the last test, and the chip (`Not calibrated` / `Listening` / `Calibrated` / `Test passed` / `Test failed`) and the feedback line under the readouts follow from it. The hook holds only what the store does not: which capture is running and why the last one fell short (no sound, permission denied or blocked, interrupted, failed). While a sound is listening its pressed button reads "Cancel" and every other Recalibrate / Test button is disabled; Test is also disabled until the sound is calibrated. A capture is cancelled when the tab loses focus or the screen unmounts. A fresh install still reads "Not calibrated" for every sound until the user calibrates, and the **Recalibrate all** button is still inert. The card's rows wrap by the system font scale (`useWindowDimensions().fontScale`) so large text stacks instead of truncating.

### Timing a run

`TimerScreen` times a run of the selected drill from the microphone. `useDrillRun` (`src/hooks/`) owns one run at a time and moves through `idle → arming → waiting → running → finished`: Start opens the microphone (`arming`), then the random delay runs (`waiting`), the beep is requested (`running`), and the run ends on its last step or when stopped (`finished`). It reads the thresholds from `useCalibration()` as they are when Start is pressed, uses the abort / run-id guards `useCalibrationCapture` uses, and stops the run when the tab loses focus or the screen unmounts. Start with a sound the drill needs still uncalibrated is refused before the microphone opens, and the header names the sounds.

`DrillRunEngine` (`src/services/drillRunEngine.ts`) does the listening. A run is `create` → `arm()` → `begin()` → `stop()`, and it emits `zero`, `stepDetected`, `runComplete` and `error`. `arm` is called before the delay so the microphone is already open when the beep sounds; `begin` is called from `StartSequenceService`'s `onTrigger`, at the instant the beep is requested, and stamps that instant with `AudioCaptureService.now()`. What counts as the beep or a step is decided by pure rules in `src/utils/runDetection.ts`, a reducer (`detect(state, reading)`) over the readings:

- **Heard and silent steps.** Only `shot`, `reload` and `rack` steps are listened for (`planRun`). A `draw`, `transition` or `holster` cannot be heard, so it is not timed and its par counts towards the next heard step: a 1.50 s draw before a 0.25 s shot makes that shot due at 1.75 s. A heard step is untimed only when nothing counted towards it has a par, and a silent step with nothing heard after it is dropped.
- **Zero point.** A phone plays a sound some time after it is asked to, so the run is timed from the beep as the microphone hears it, not from the request. The beep is the first sound within `beepSearchMs` (600 ms) of the request that rises 12 dB over the room and is a tone (its peak no more than 7 dB over its RMS level, which a shot or a click never is); zero is where it first reaches half its level. Nothing is taken for a step while the beep may still come: readings are held, dropped when the beep is found (a bang from the next lane before the beep is not a shot of this run), and handed to the step rules once the 600 ms are up. In that case zero is the request (`zeroSource: 'trigger'`) and the screen says the first step may read long. A beep that takes longer than that to sound, as some wireless speakers do, is not recognised and can be counted as a step.
- **A step** is a reading whose peak reaches the expected step's threshold, at least 60 ms after zero, at least 70 ms after the previous step, and after the level has dropped 3 dB under that threshold since the previous step. While the beep is still sounding it must also be 6 dB louder than the beep. It is timed at the reading's `peakTimestamp`; a step that peaks within 5 ms of the end of its buffer waits one reading, and takes that reading's peak when it is louder and within 5 ms.
- The margins are `DEFAULT_DETECTION_TUNING` and can be overridden per run.

Every time in a run comes from the readings' own timestamps on the capture clock, never from when a reading reaches JS, so a busy JS thread delays the screen and not the result. The native module times readings off the audio hardware's own count of frames (`CaptureClock.kt`, `AudioRecord.getTimestamp`) when the device has one: the hardware says which frame it had reached at which time, and a line drawn through the middle half of the last 32 such anchors gives any frame's capture time however late its read returned. One anchor stamped late cannot move that line, an anchor the hardware repeats is counted once, and once the clock is adopted an anchor more than 100 ms off the line is ignored. It is adopted only inside the first three quarters of a second of a capture, once at least eight anchors covering 300 ms agree with the capture rate to within 2%; a device that never gets there is timed by when each read returned, which can be a hardware burst (about 20 ms) off. A reading says which through `frameTimed`, which is also false while the line is on the move or has had no anchor for two seconds, and a finished run says it through `clockSource`. The switch steps the timeline back once, so nothing is timed against the first `CAPTURE_CLOCK_SETTLE_MS` (750 ms) of a capture; the start delay's 1000 ms minimum keeps the beep clear of it, and a test ties the two together. `onsetTimestamp` is where a buffer's sound first reached half its peak, which is what times the beep.

On screen, each heard step's row fills in with its time and its difference from par (worded `0.35s under` / `0.10s over` / `on par`, not colour alone), the clock runs from zero and holds the run time at the end, and a caption under the splits says how the run was timed. The clock's tick lives in a small `RunClock` component so the rest of the screen does not redraw during a run. Stop ends a run early and keeps the steps heard, and the drill chips do nothing while a run is on. A failure and a finished run are announced once, together when they arrive together, and not over another tab. Level-only detection means any sound at least as loud as the expected step's threshold counts as that step.

### Appearance state (`src/store/AppearanceContext.tsx`)

`AppearanceProvider`, mounted in `App.tsx` outside `CalibrationProvider` and the navigators, reads the profile's `appearance` once through `ProfileStorageService` and **renders nothing until it has**, so a pinned theme is right from the first frame; a failed read falls back to `system`. `useAppearance()` exposes `preference` and `setPreference`, which applies the choice at once, saves it with `updateProfile({ appearance })`, and on failure puts back the last saved choice (only if no newer choice was made since) and rejects. `useTheme()` reads this context and resolves the mode with `resolveThemeMode` in `theme.ts`: a pinned `light` / `dark` wins, `system` follows `useColorScheme()`; with no provider (a component rendered alone in a test) it follows the OS. The native window background and system dialogs still follow the device, so a cold start shows the device's background for a moment before the first frame. The provider takes an optional `storage` (`load` / `update`) so tests can inject fakes.

### Drill editor

`SequenceEditorScreen` (route `SequenceEditor`, pushed over the tabs) is the create / edit drill screen: a name field, one row per step (`DrillStepRow` in `src/components/`: number, type dropdown, par pill, remove button), an "Add step" row, and a Preview card with the sequence and each par. The draft lives in `useDrillEditor` (`src/hooks/`) as a name and a `DrillStep[]`; opened with an `id` it reads that drill once through `DrillStorageService.loadById` (with loading, not-found and failed-read states), without one it starts empty. With two or more steps a **Reorder** action on the Steps header puts the list in reorder mode: each row swaps its par and remove controls for Move up / Move down buttons (disabled at either end) until **Done** is pressed. A move keeps the step's id, type and par, and is announced to a screen reader like add and remove. There is no drag to reorder.

**Saving** goes through the hook's `save()`: a new draft is created with `DrillStorageService.save`, an opened drill is changed in place with `DrillStorageService.update` (same id and `createdAt`, step ids kept), and the service derives `totalPar` / `shotCount` — the editor never computes the stored totals itself. `save()` never rejects; it resolves to the stored `Drill`, or `null` when nothing was stored or the editor was closed before the write landed, and the screen only announces and goes back on a drill. The Create drill / Save changes button is enabled by `canSave`: the draft has no `problems` (`drillDraftProblems` in `src/utils/drillDraft.ts` — no name, no steps, plus the two limits the editor's own controls already prevent) and no save is running. The line under the button says which of those is missing. `saveState` is `idle` / `saving` / `saved`; `saved` is final so a double tap cannot store a new drill twice, and the button reads "Saving…" from the press until the screen is gone. The draft only takes changes while `idle` — every mutator in the hook refuses otherwise — so what is stored is what was on screen when save was pressed. A failed save keeps the draft, returns to `idle` and sets `saveFailure` (`invalid` / `missing` / `failed`), which the screen words for the shooter above the button. Leaving any other way drops the draft without asking.

The step-list rules are pure functions in `src/utils/drillDraft.ts`: the first step added is a draw and every later one a shot, both untimed; a step added in the editor gets its id there, so rows keep their identity as others are removed or moved; `moveStep` moves a step to a position and leaves the list unchanged for an unknown id or a position out of range; the list stops at `MAX_DRILL_STEPS`; `parseParInput` turns typed text into a par rounded to the hundredth, or `null` when the storage service would reject it. The editor offers five step types (`EDITOR_STEP_TYPES`: draw, shot, reload, rack, holster). `transition` is still a valid stored type, so a stored transition step shows as one and keeps it until changed, but it cannot be picked for another step. Step names (`stepTypeLabel`, and `stepLabel` for the numbered "Shot 2" form) live in `src/utils/drill.ts`. A par is picked in `ParPickerSheet` (`src/components/`): a custom time or a preset row.

On Android a touchable that is both rotated and given a `hitSlop` stops receiving presses, so the remove button keeps its 45° rotation, and the move buttons their ±90° chevrons, on an inner view.

### Deleting a drill

A drill is deleted from the Drills list, not from the editor: swiping its row left reveals a red Delete action, and pressing it opens `ConfirmSheet` (`src/components/`), which names the drill. Confirming calls `useDrills().deleteDrill`, which removes the drill through `DrillStorageService.deleteById` and takes it off the list; it never rejects and resolves to `false` when the delete failed, in which case the sheet stays up with the reason and the drill stays listed. While the delete runs the sheet cannot be dismissed, and a ref guards against a second confirm. A swipe on its own never deletes. Deleting a drill leaves its sessions alone: the runs recorded with it stay stored with a `drillId` that no longer resolves.

The row is `SwipeableRow` (`src/components/`): a pan from `react-native-gesture-handler` (`usePanGesture` + `GestureDetector`, callbacks on the JS thread) moving a built-in `Animated` value. `react-native-reanimated` is not installed, so the library's own `ReanimatedSwipeable` is not an option. Whether a row rests open is the screen's state (`openRowId`), so only one row is open at a time; a tap on an open row closes it instead of opening the editor, and leaving the tab closes it. The rules of the swipe (how far the row follows the finger, when a release ends open) are pure functions in `src/utils/swipe.ts`. The Delete action is hidden from a screen reader while the row is closed; TalkBack reaches delete through a `Delete drill` accessibility action on the row instead. The settle animation is skipped when the device asks for reduced motion (`useReduceMotion` in `src/hooks/`).

Anything that renders `SwipeableRow` in a test needs a `GestureHandlerRootView` around it; swipes are driven with `fireGestureHandler` / `getByGestureTestId` from `react-native-gesture-handler/jest-utils`. Jest's window has a font scale of 2, which doubles the action's width, so a test swipes well past it rather than by an exact distance.

### History list

`HistoryScreen` (route `HistoryList`, the History tab's landing screen) shows the Runs and Drills counters and one row per drill that has been run: its name, run count, best total time and how long ago the last run was (`3 runs · Best 4.21s · 2d ago`), most recently run first. `useDrillHistory` (`src/hooks/`) reads every session and every drill on each focus, the same way `useDrills` does (loading, error with a retry, and a refresh that keeps the list it had), and groups them with `summarizeDrillHistory` in `src/utils/history.ts`. The Runs counter is every stored session; the Drills counter is the number of drills with at least one run, so it is the number of rows, not the size of the library the Profile screen counts. Both read `—` until the history has loaded.

A session holds its drill's id and not its name, so the name comes from the drill as it is now: a renamed drill shows under its new name, a drill with no runs is not listed, and the runs of a deleted drill stay listed under `DELETED_DRILL_NAME` ("Deleted drill"). `formatTimeAgo` in `src/utils/format.ts` words the last run in whole counts of the largest unit that fits (`just now`, `5m`, `3h`, `2d`, `3w`, `4mo`, `2y`), and each row carries a spoken label (`spokenSeconds`, `spokenTimeAgo`) through `ListRow`'s `accessibilityLabel` so TalkBack does not read the abbreviations. A `ListRow` subtitle wraps to a second line rather than truncating, so the row keeps its "ago" at the largest text size. Tapping a row pushes `HistoryDetail` with the drill's id and name.

### History detail

`HistoryDetailScreen` (route `HistoryDetail`) shows every run of one drill: a Best / Avg card, then one card per run, newest first, with the date and time it was made (`formatDateTime`: `Oct 12, 2026 · 6:52 PM` in the device's own form), its total time and a chip with the difference from the run before it (`-0.08s vs previous`; the first run of a drill has none). `useDrillRuns` (`src/hooks/`) reads `SessionStorageService.loadByDrillId` and `DrillStorageService.loadById` on each focus, the same way `useDrillHistory` does. The title is the `drillName` param until the drill has been read, then the drill's current name, or `DELETED_DRILL_NAME`. The figures come from pure functions in `src/utils/history.ts`: `summarizeRuns` (best and average), `describeRuns` (order and the difference, rounded to the millisecond) and `shownDeltaSign`, which judges a difference as it reads to the hundredth so one shown as `0.00s` is never coloured or worded as faster or slower.

A drill can be run any number of times, so the cards are a `FlatList` inside a non-scrollable `Screen`: the title and back button stay put and the list scrolls under them, with the summary card as its header and the loading / error / empty card as its empty component. The card is `RunCard` (`src/components/`, memoised). Its whole header is one button that shows or hides the Step / Par / Actual / Δ breakdown, taken from the session's splits as stored (an untimed step shows `—` for par and Δ). The newest run starts open; the screen only keeps the cards the shooter has pressed (`toggled`, by session id). Above a font scale of 1.2 the four columns no longer fit, so each step stacks its name over three captioned figures; above 1.3 the summary card puts Avg under Best and a run card puts its total time under its date. Every card and every step carries a spoken label (`spokenDateTime`, `spokenSeconds`: "Shot 1, par 0.25 seconds, took 0.31 seconds, 0.06 seconds over par").

Run comparison and a personal-best badge are not on this screen; they are separate pieces of work.

### Services (`src/services/`)

- **`storage.ts`** — the only module that may touch AsyncStorage. `createStorageNamespace<T>({ name, version })` returns typed CRUD scoped to keys of the form `@BrassCount:<name>:<version>:<id>`. All failures surface as `StorageError`; corrupt JSON reads resolve to `null` / are skipped rather than throwing. Bump `version` and write a migration for breaking shape changes.
- **`sessionStorage.ts`** — sessions (completed runs of a drill), one key per session. `saveSession` always creates: the service generates the id, stamps `createdAt` and derives each split's `delta` through `src/utils/session.ts` (`null` when the step has no par). A session is never updated after it is saved, so there is no change queue. `loadSessions()` and `loadSessionsByDrillId()` return newest-`createdAt` first; the by-drill read loads every session and filters. Each stored value is a `{ schemaVersion, session }` envelope, handled like a drill's: a `Session` shape change bumps `SESSION_SCHEMA_VERSION` and upgrades older envelopes in `parseStoredSession`, reads are validated field by field, and an entry that fails is skipped. The limits (`MAX_SESSION_SECONDS`, `MAX_SPLIT_LABEL_LENGTH` in `src/types/session.ts`, plus `MAX_DRILL_STEPS` and `MAX_STEP_PAR_SECONDS`) apply on save and read. Throws `SessionStorageError` (a `StorageError` with a `code`).
- **`drillStorage.ts`** — drills, one key per drill. `saveDrill` creates (the service generates the drill id and step ids), `updateDrill` changes an existing one and rejects with `NOT_FOUND` otherwise. It stamps timestamps and derives `totalPar` / `shotCount` through `src/utils/drill.ts`; `totalPar` is `null` when any step is untimed. Each stored value is a `{ schemaVersion, drill }` envelope: a `Drill` shape change bumps `DRILL_SCHEMA_VERSION` and upgrades older envelopes in `parseStoredDrill`. Reads are validated field by field and an entry that fails is skipped. The limits in `src/types/drill.ts` (`MAX_STEP_PAR_SECONDS`, `MAX_DRILL_STEPS`, `MAX_DRILL_NAME_LENGTH`) apply on save and read. Changes to stored drills are queued (`createSerialQueue` in `src/utils/serialQueue.ts`) and run one at a time, so overlapping updates and deletes cannot lose an edit. Throws `DrillStorageError` (a `StorageError` with a `code`).
- **`profileStorage.ts`** — the local profile: display name, handle and the Appearance preference (`system` / `light` / `dark`), with no account behind it. An install has exactly one, under the single key `@BrassCount:profile:v1:local`. `loadProfile()` always resolves to a `Profile` — `DEFAULT_PROFILE` (no name, no handle, `system`) until one is saved. `updateProfile(changes)` is the only write and creates the profile on first use: omitted fields are kept, `null` or a blank string clears the name or handle, whitespace runs in the name collapse to one space, the handle is stored with its leading `@` whether or not one was passed, and `updatedAt` is stamped. The stored value is a `{ schemaVersion, profile }` envelope like a drill's, but a field that fails validation on read falls back to its default on its own instead of discarding the whole profile, so a bad name cannot reset the theme. The limits in `src/types/profile.ts` (`MAX_PROFILE_NAME_LENGTH`, `MAX_PROFILE_HANDLE_LENGTH`) apply on save and read. Updates and clears are queued like drill changes. Throws `ProfileStorageError` (a `StorageError` with a `code`).
- **`beepPlayer.ts`** — `BeepPlayer` interface (`prepare`/`play`/`release`) with an oscillator implementation over `react-native-audio-api`'s `AudioContext`.
- **`startSequence.ts`** — waits a random delay (default 1000–5000 ms), plays the beep, resolves `{ startedAt, delayMs }`. `startedAt` is wall-clock time taken when the beep is requested; `onTrigger` is called at that same instant, for a caller that times on another clock. Cancellation is via `AbortSignal` and rejects with `StartSequenceAbortError` (distinct from `StartSequenceError`, which is a real failure).
- **`audioCapture.ts`** — the wrapper over the native `AudioCapture` TurboModule: permission, `start` / `stop`, the amplitude and error streams, and `now()`, the clock the readings are stamped with. `resolveMicrophonePermission` (granted already, or the outcome of asking) is shared by everything that opens the microphone.
- **`drillRunEngine.ts`** — one run of a drill: `createDrillRun(options)` returns a handle with `arm` / `begin` / `stop` and `on(event, listener)`. It owns the microphone and the events; the rules are in `src/utils/runDetection.ts` (see "Timing a run"). `stop()` resolves the run as far as it got and never leaves the microphone open. Throws and emits `DrillRunError` with a `code` (`NOT_CALIBRATED` with the `sounds`, `NO_DETECTABLE_STEPS`, `PERMISSION_DENIED`, `PERMISSION_BLOCKED`, `INTERRUPTED`, `CAPTURE_FAILED`, `INVALID_STATE`); a cancelled `arm` rejects with `DrillRunAbortError`.
- **`calibrationCapture.ts`** — `captureSample()` listens to the microphone for a fixed window through `AudioCaptureService` and resolves `{ peakDbfs }`, the loudest `peakDb` heard (`DBFS_MIN` for silence; readings that are not a finite level at or below 0 are ignored). It requests the microphone permission when it is missing and always stops capture and unsubscribes, however it ends. What the level means is the caller's business (`src/utils/calibration.ts`). Throws `CalibrationCaptureError` with a `code` reduced to what the user can do (`PERMISSION_DENIED`, `PERMISSION_BLOCKED`, `INTERRUPTED`, `CAPTURE_FAILED`); cancellation is via `AbortSignal` and rejects with `CalibrationCaptureAbortError`.

Service conventions to follow when adding one: export plain functions **and** an object-form `XxxService` handle plus `XxxServiceType`; throw a named `Error` subclass carrying `cause`; accept collaborators (`player`, `random`, `signal`) through an options object so tests inject fakes instead of mocking modules. Re-export from `src/services/index.ts`.

### Navigation (`src/navigation/`)

Root native stack → `Tabs` (bottom tabs: Calibration, Drills, **Timer** as initial route, History, Profile) + `SequenceEditor` pushed over the tabs. The History tab is itself a nested stack (`HistoryList` → `HistoryDetail`) so the tab bar stays visible on the detail screen. All param lists live in `src/types/navigation.ts`, which also augments `ReactNavigation.RootParamList` globally.

Navigator headers are off everywhere: each screen renders its own header through the `Screen` component, and the bottom chrome is the custom `TabBar`. A new tab needs an entry in `tabIcons` in `TabBar.tsx`.

### Theming

`src/theme/theme.ts` defines a raw palette and semantic tokens (`colors`, `spacing`, `radius`, `typography`, `elevation`) for light and dark themes with an identical shape.

- Components never import the palette or theme objects directly (type-only `Theme` imports are fine). Get tokens from `useTheme()`, which applies the Appearance preference in one place.
- Styles are written as a module-scope `createStyles = (theme: Theme) => StyleSheet.create({...})` and consumed with `useThemedStyles(createStyles)`. The factory must be module-scope (or memoised) or the memo is defeated.
- Use spacing/radius tokens and `Typography` variants rather than literal numbers and ad hoc font sizes. Timer and metric readouts use the mono variants (`timer`, `metric`, `metricSmall`) so digits don't jitter.
- Adding a semantic color means adding it to `SemanticColors` and both `lightColors` and `darkColors`.

Screens are composed from the primitives in `src/components/` (`Screen`, `Card`, `ListRow`, `Chip`, `SectionHeader`, `Typography`, `Icon`, …). `Screen` owns safe area, padding, title/subtitle/back control, and bottom padding to clear the tab bar — pass `scrollable` for anything that can overflow.

## Conventions

### Path aliases

Aliases (`@/`, `@components/`, `@screens/`, `@navigation/`, `@hooks/`, `@utils/`, `@constants/`, `@types/`, `@services/`, `@store/`, `@api/`, `@assets/`) are declared in three places that must be kept in sync: `tsconfig.json`, `babel.config.js`, `jest.config.js`.

Existing usage: `@/theme/theme`, `@/types/...` and `@/screens` go through `@/`; everything else uses the specific alias and imports the concrete file (`@components/Card`, `@hooks/useTheme`), not the barrel. Tests import with relative paths (`../src/...`).

### Import order (lint-enforced, and warnings fail the build)

`react` first, then `react-native`, then other external packages, then internal aliases, then relative — each group separated by a blank line and alphabetised within the group. `npm run lint:fix` sorts them.

### ESLint config

ESLint 9 reads the flat config `eslint.config.js`, which pulls its `rules`, `settings` and ignore list out of `.eslintrc.js`. Edit rules in `.eslintrc.js`; edit file globs/parser options in `eslint.config.js`. Root config files are ignored by ESLint (and filtered out in `.lintstagedrc.js`) — add any new root config file to both lists.

### Tests

A behaviour change ships with unit tests in the same change: Jest for TypeScript / React Native, JVM unit tests for Kotlin under `android/`, and both when a native module's contract changes. See `.claude/rules/common/testing.md` and `.claude/rules/kotlin/testing.md` (Kotlin tests are plain JUnit 4 under `android/app/src/test/java/`, run with `testDebugUnitTest` locally and in CI; they cover the pure audio maths extracted from the native module, not its threading or lifecycle).

Tests live in `__tests__/` at the repo root. `jest.setup.js` globally mocks AsyncStorage (official in-memory mock), `react-native-audio-api` (its `/mock`), the app-local `NativeAudioCapture` spec and gesture-handler. Component tests use `react-test-renderer` with `act`, wrap in `SafeAreaProvider` with `initialMetrics`, and query by the `testID`s the screens expose (`btn-start`, `text-elapsed`, `tab-<Route>`, …). Timing-dependent tests use Jest fake timers with `jest.setSystemTime`.

### Commits, branches, PRs, versioning

- Commit subjects must match `<type>(optional-scope): <description>` — the husky `commit-msg` hook rejects anything else. Types: `feat`, `fix`, `add`, `chore`, `docs`, `refactor`, `test`, `build`, `ci`, `perf`, `style`, `revert`.
- `pre-commit` runs lint-staged (`eslint --fix --max-warnings=0` + `prettier --write`) on staged files.
- Branches are `<type>/<kebab-description>` (e.g. `feat/start-sequence-service`). The Tests and Android build workflows only trigger on pushes to `main` and branches matching `feat*/*`, `fix*/*`, `chore*/*`, `refactor*/*`, `build*/*`, `test*/*`, `ci*/*`.
- PR titles use the same conventional format. Fill in the PR template's "Type of Change" checkboxes — the autolabeler reads them.
- **Never hand-edit version numbers.** On merge to `main` a bot bumps `package.json`, `package-lock.json` and `VERSION.txt` and creates a `v*` tag. The bump is a patch unless the PR title contains `#minor` or `#major` (e.g. `feat(timer): add start beep #minor`).

## Known stale spots

- `.github/copilot-instructions.md` describes a Zustand store, `src/store/`, `src/api/`, a `counterStore` test and a `__mocks__/` directory — none of these exist. Don't treat it as a description of the current code.
- `docs/CONTRIBUTING.md` shows branch names as `feat: short-description`; the real convention is the slash form above.
- `react-native-dotenv` is configured (`import { X } from '@env'`), but nothing imports `@env` yet and the files its aliases point to (`__mocks__/@env.js` for Jest, `src/types/env.d.ts` for TypeScript) don't exist — create both when first using it.
